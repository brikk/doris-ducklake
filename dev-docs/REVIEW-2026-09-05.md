# Code Review: 2026-09-05

Reviewed connector commit `5b1179b65ed1e8f3f3e6a99c91a9cff0dcbc967f` on `main`,
including the pre-existing, uncommitted catalog dependency change from `0.7.0`
to `0.7.1`. That change was not made or modified by this review.

Scope: first-party production Kotlin, tests and corpus adapter, Gradle delivery,
Compose tooling, and existing review/TODO documents. Relevant catalog, DuckLake,
DuckDB, and Doris implementations were traced where a finding crosses that
boundary. This is not a comprehensive audit of those upstream projects.

**W00: Overall assessment.** The architecture is sensible and the project has valuable
interop tests, but correctness and operational safety are weaker than the green
test count and some support claims suggest. Keep the pre-alpha warning. Prioritize
data protection and silent wrong-result paths before adding features.

## Reading This Review

### Stable Identifiers

Every finding, prior-item status, nit, strength, assessment, and validation entry
has a stable ID. An ID covers the entire item: its claims, examples, evidence,
caveats, and recommended action. It is not a severity or priority rank.

| Prefix | Meaning |
|---|---|
| `F01`-`F26` | P1 findings; existing identifiers preserved. |
| `M01`-`M20` | P2 findings; existing identifiers preserved. |
| `O01`-`O13` | Prior-review items and their reconciled status, including resolved items and non-goals. |
| `N01`-`N27` | Remaining nits and contract-hardening items. |
| `S01`-`S08` | Strengths worth preserving. |
| `W00`-`W04` | Overall assessment and cross-cutting weaknesses. |
| `V01`-`V07` | Executed validation evidence. |
| `L01`-`L04` | Review/validation limitations. |

**Communication contract:** "do F01" means revalidate F01 against the current
code/dependencies, implement its recommended remediation, add/run appropriate
regression tests, and record the outcome under that ID. "Do N07" works the same
way; "explain W01" or "verify S03" addresses an assessment rather than a fix.
An ID does not authorize destructive live operations, expand a documented non-goal,
or imply that an upstream fix can be completed in this repository.

Keep IDs unchanged when items are fixed, reprioritized, or moved. Append new IDs
within the appropriate prefix; never recycle one. Keep closed items with their
resolution, commit/reference, and verification evidence. If an item is split,
append child suffixes such as `F04.a` and `F04.b`; the parent continues to refer to
the whole group. In another review document, qualify an ambiguous ID as
`REVIEW-2026-09-05/F01`. Priority-list positions are not identifiers.

### Evidence And Severity

- **P1:** fix before trusting the affected operation with real data. This includes
  silent wrong results, destructive scope/authorization mistakes, and unreliable
  validation gates. These are conditional defects, not claims that every query fails.
- **P2:** concrete functionality, reliability, or verification gaps that should
  follow the P1 work.
- **Nits:** cleanup and contract hardening without an established ordinary-path
  correctness failure. Known unsupported features are listed separately.
- Unless explicitly described as executed, a finding is **source-traced**, not
  reproduced on a running FE/BE. Suggested regression tests are recommendations,
  not tests added by this review. Some metadata findings were additionally checked
  with in-memory probes against the selected catalog dependency.
- Source links and line numbers refer to the reviewed tree. Doris-specific claims
  target `4ab2cd71095`, plugin API `6.0`, not an unspecified release BE.

## P1 Findings

### F01: Referenced Objects Can Be Deleted

**Where:** [S3WarehouseBlobStore.kt:48-78](../src/dev/brikk/ducklake/doris/plugin/S3WarehouseBlobStore.kt#L48-L78),
[DuckLakeProcedureOps.kt:310-340](../src/dev/brikk/ducklake/doris/plugin/DuckLakeProcedureOps.kt#L310-L340),
[OrphanFiles.kt:49-58](../src/dev/brikk/ducklake/doris/plugin/OrphanFiles.kt#L49-L58).

The real S3 lister returns `s3://` URIs, but ownership paths preserve accepted
`s3a://` and `s3n://` aliases. Orphan selection compares strings exactly. A live,
aged `ducklake-live.parquet` referenced as `s3a://b/t/ducklake-live.parquet` is
therefore absent from the known set when listed as `s3://b/t/ducklake-live.parquet`.
The non-dry-run procedure deletes it. Retention does not protect old live data.

The resolved catalog ownership path must actually use the alias; changing only a
fallback property need not trigger it. The production lister's normalization is
not reproduced by the current fake lister, so existing tests miss the mismatch.

**Action:** compare canonical storage identities on both sides, preserving object
key bytes. Test mixed absolute/relative paths and all accepted S3 schemes using a
fake that reproduces the real lister. Do not broaden the managed-file deletion gate.

### F02: Maintenance Exceeds Caller Authority

**Where:** [DuckLakeProcedureOps.kt:108-180](../src/dev/brikk/ducklake/doris/plugin/DuckLakeProcedureOps.kt#L108-L180).

Doris's pinned `ConnectorExecuteAction` checks `ALTER` on the named table. The
connector ignores session identity and runs expiry/cleanup catalog-wide using
shared JDBC/storage credentials. A user granted ALTER on table A can expire
history involving table B without catalog-wide authority. Explicit snapshot IDs
also bypass the retention floor. The latest snapshot remains protected.

The result's catalog-wide disclaimer is useful documentation, not authorization.
This is reachable under built-in table-level grants; deployments that withhold
those grants or enforce a stronger custom policy can avoid exposure.

**Action:** require catalog-wide authority before catalog-wide maintenance and
equivalent wider authority for widened orphan scopes. If the SPI cannot express
that check, gate these operations to an explicit administrative deployment mode.
Add a two-table, table-scoped-grant authorization regression.

### F03: Reordered INSERT Columns Swap Values

**Status:** Implemented and locally regression-tested; live FE/BE verification pending.

**Where:** [DuckLakeWritePlanProvider.kt:48-49](../src/dev/brikk/ducklake/doris/plugin/DuckLakeWritePlanProvider.kt#L48-L49).

At the reviewed baseline, the provider inherited `requiresFullSchemaWriteOrder() = false`, but emitted a full,
catalog-ordered Iceberg schema for a positional BE writer. Doris preserves the
user's explicit column order on that default path. For `t(a INT, b INT)`:

```sql
INSERT INTO t (b, a) VALUES (20, 10);
```

The baseline's traced write is `(a=20, b=10)`, not `(a=10, b=20)`. Equal types and full arity
avoid the checks that might otherwise turn this into an error. Partial-column
INSERT can instead fail the BE column-count check.

**Original action:** override `requiresFullSchemaWriteOrder()` to return true, as the native
Iceberg provider does. Test reversed same-type columns, omitted columns/defaults,
and reordered partition columns through FE binding and cross-engine read-back.

**Resolution (2026-09-05):** the provider now returns
true from `requiresFullSchemaWriteOrder()`, matching the native Iceberg provider.
Pinned Doris `BindSink.java:941-975` uses that declaration to project expressions
to full-schema order and fill omitted columns. No connector-side row-reordering
implementation, additional write capability, or default-value change was added.

**Regression coverage:**
[DuckLakeWritePlanProviderTest.kt:94-119](../test/src/dev/brikk/ducklake/doris/plugin/DuckLakeWritePlanProviderTest.kt#L94-L119)
asserts the required SPI declaration and checks that reversed and partial explicit
column lists still produce the complete catalog-ordered sink schema for
unpartitioned, identity-partitioned, and bucket-partitioned tables. The schema
test checks the connector's half of the contract, not FE expression binding or
the values written by the BE.

**Verification:**

- Before the override, `./gradlew test --tests '*DuckLakeWritePlanProviderTest'`
  failed specifically on the new write-order declaration assertion (6 tests, 1
  failure). Gradle ran on Java 25.0.2.
- After the override, the same six provider tests passed on Java 17.0.2 using the
  temporary launcher init script described in V05.
- `./gradlew test detekt assemble` on Java 25.0.2 passed: **242 passed, 1 skipped,
  0 failures**, plus static analysis and plugin packaging. These are post-fix
  results; V01-V07 retain the original review evidence.

**Remaining to close F03:** run exact-value reversed same-type, omitted-column
(NULL/default), and reordered partition-column INSERT checks through a freshly
loaded fixed plugin and DuckDB read-back on an isolated compatible FE/BE stack.
No suitable stack was running during this change; the active Trino-owned release
stack was left untouched. Shared-lake smoke was not run. Do not treat the local
schema tests as live write verification, or this ordering fix as resolving M04's
separate default-persistence defect.

### F04: Bucket Pruning Is Not Evolution-Safe

**Where:** [DuckLakeConnectorMetadata.kt:263-306](../src/dev/brikk/ducklake/doris/plugin/DuckLakeConnectorMetadata.kt#L263-L306).

Two related failures violate the retained-file-set contract:

- The retained universe is `getFilePartitionValues(...).keys`, which omits files
  without partition-value rows. Files written before an unpartitioned-to-bucket
  ALTER disappear even when they contain matching rows.
- The current specification is applied by `partitionKeyIndex` without retaining
  each file's `partitionId`. After changing `bucket(4, s)` to `bucket(8, s)`, an
  old `alice` file in bucket 1 is compared against the new target bucket 5 and lost.

Both cases were exercised with in-memory catalog interleavings/fixtures; existing
bucket tests principally cover an unchanged spec.

**Action:** start with every snapshot-visible file and use its own specification.
Keep files with absent, retired, or unresolvable partition metadata rather than
guessing. Add unpartitioned-to-bucket, bucket-count, key-order, and column-change tests.

### F05: Unsigned Bucket Hashing Uses Signed Encoding

**Where:** [DuckLakeConnectorMetadata.kt:289-297](../src/dev/brikk/ducklake/doris/plugin/DuckLakeConnectorMetadata.kt#L289-L297),
[DuckLakeBucketTransform.kt:29-36](../src/dev/brikk/ducklake/doris/plugin/DuckLakeBucketTransform.kt#L29-L36).

Bucket encoding is selected from the literal's JVM class instead of the source
DuckLake type. DuckLake's inspected unsigned integer path hashes its textual
representation, while the widened Doris integral literal is hashed as eight-byte
signed integer data. For unsigned value `1` with four buckets, those produce 3
and 0 respectively. Equality pruning can remove the matching file.

**Action:** make hashing source-type-aware or decline pruning for unverified
types. Add DuckDB-oracle cases for `uint8`, `uint16`, and `uint32`, including bounds.

### F06: Unicode Range Construction Is Unsound

**Where:** [DuckLakePredicateConverter.kt:91-124](../src/dev/brikk/ducklake/doris/plugin/DuckLakePredicateConverter.kt#L91-L124).

Membership spans use Java UTF-16 `String.compareTo`, but catalog `0.7.1` compares
VARCHAR bounds by code point. `IN (U+E000, U+1F600)` produces bounds reversed in
the catalog's ordering. Prefix-LIKE successor construction increments a UTF-16
code unit; a prefix ending in U+103FF becomes an invalid surrogate sequence rather
than U+10400. These are exclusion bounds, so residual predicate evaluation cannot
recover rows from a discarded file.

**Action:** use one code-point ordering contract and a Unicode-scalar successor,
or decline the unsafe shapes. Test BMP/supplementary mixtures, surrogate boundaries,
maximum code points, and exact retained-file identities.

### F07: Snapshot IDs Do Not Fence Physical Rewrites

**Where:** [DuckLakeConnectorMetadata.kt:215-246](../src/dev/brikk/ducklake/doris/plugin/DuckLakeConnectorMetadata.kt#L215-L246),
[DuckLakeScanPlanProvider.kt:137-190,234-268](../src/dev/brikk/ducklake/doris/plugin/DuckLakeScanPlanProvider.kt#L137-L268).

Related planning reads run independently, with no catalog `readSession`. A logical
snapshot pin is not a stable physical representation when flush/partial compaction
backdates replacement files and removes the previous representation.

- Predicate A can retain file 10, a rewrite replaces it with file 20, and predicate
  B retains 20. Intersecting the sets returns empty although both predicates match.
- Planning can enumerate no files before an inline flush, then find no inline rows
  after it. The result is an empty scan. This also bypasses the default inline-read
  refusal and can affect COUNT; the experimental flag is not required.
- A pruned ID set can become stale between `applyFilter` and later range planning.

**Action:** collect dependent metadata under a coherent read session and carry
that physical view through downstream planning, or revalidate/retry it. Merely
wrapping each individual lookup is insufficient. Add barrier-controlled flush and
rewrite tests across predicate collection, scan-property generation, and range planning.

### F08: Historical Reads Apply Future Deletes

**Where:** [DuckLakeScanPlanProvider.kt:404-408,771-788](../src/dev/brikk/ducklake/doris/plugin/DuckLakeScanPlanProvider.kt#L771-L788),
[DuckLakeScanRange.kt:155-169,295-315](../src/dev/brikk/ducklake/doris/plugin/DuckLakeScanRange.kt#L295-L315).

The existing partial-file guard covers data files, not per-row visibility inside
delete files. DuckLake flush can write
`(file_path, pos, _ducklake_internal_snapshot_id)` entries from multiple deletion
snapshots into a file active at an earlier snapshot. Doris's
Iceberg reader reads only `file_path` and `pos` and applies every position.

Insert IDs 1-4 together, delete 1 at S1 and 2 at S2, then flush. A read at S1 can
return `{3,4}` instead of `{2,3,4}`. The upstream-produced shape can have null
`deleteFilePartialMax`, so checking only that metadata is insufficient.

**Action:** filter the embedded snapshot column or reject historical delete reads
whose safety cannot be established. Add the existing catalog delete-snapshot
fixture to Doris read coverage. This is distinct from both partial-data-file
guarding and the previously fixed OPTIONAL-column compatibility problem.

### F09: Lossy Timestamp Mapping Breaks Pruning

**Where:** [DuckLakeTypeMapping.kt:112-116](../src/dev/brikk/ducklake/doris/plugin/DuckLakeTypeMapping.kt#L112-L116),
[DuckLakePredicateConverter.kt:127-151](../src/dev/brikk/ducklake/doris/plugin/DuckLakePredicateConverter.kt#L127-L151).

`timestamp_ns` is exposed at microsecond precision, but predicates are applied to
nanosecond storage statistics without widening. A file containing only
`2026-01-01 00:00:00.000000001` is visible to Doris as the exact microsecond
`2026-01-01 00:00:00.000000`. Equality to that visible value is forwarded as a point
range below the file minimum, incorrectly pruning it.

**Action:** decline pruning for lossy mappings or translate predicates into
conservative source-domain intervals. Test equality, IN, BETWEEN, upper bounds,
and pre-epoch conversion. A correct type descriptor does not prove safe pruning.

### F10: Timestamp Time Travel Loses Precision

**Where:** [DuckLakeConnectorMetadata.kt:405-420](../src/dev/brikk/ducklake/doris/plugin/DuckLakeConnectorMetadata.kt#L405-L420).

A textual Instant is converted to epoch milliseconds and back before catalog
lookup. Requesting a commit at `.123456Z` resolves at `.123000Z` and can select the
previous snapshot. An in-memory probe reproduced that boundary selection.

**Action:** preserve the parsed Instant; use epoch milliseconds only for the
explicit numeric form. Test exact commit times and adjacent microsecond instants.
Ordinary SQL timestamp syntax has a separate parsing defect listed under P2.

### F11: Imported Field IDs Override Authoritative Names

**Where:** [DuckLakeSchemaDictionary.kt:76-80,163-171](../src/dev/brikk/ducklake/doris/plugin/DuckLakeSchemaDictionary.kt#L163-L171),
[DuckLakeScanPlanProvider.kt:861-872](../src/dev/brikk/ducklake/doris/plugin/DuckLakeScanPlanProvider.kt#L861-L872).

Native DuckLake Parquet IDs equal catalog column IDs; arbitrary `add_files`
imports need not. DuckLake maps imported columns by its registered name mapping,
but Doris prefers embedded field IDs when present. Importing `(a=10,b=20)` with
physical IDs `a=2,b=1` into catalog IDs `a=1,b=2` can swap the values in Doris.

**Action:** make the registered mapping authoritative per file, or reject incompatible
embedded IDs until that transport exists. Test swapped and unrelated source IDs,
including predicates. This is broader than the documented id-less DROP/re-ADD gap.

### F12: Nested Dictionary Omission Is Unsafe On V2

**Where:** [DuckLakeSchemaDictionary.kt:42-52,70-80](../src/dev/brikk/ducklake/doris/plugin/DuckLakeSchemaDictionary.kt#L42-L80).

The comment says omitted nested columns fall back to names. On pinned Doris
`FileScannerV2`, a logical file schema with IDs throughout selects field-ID
matching independently of dictionary presence. An omitted nullable native
`STRUCT(x INT)` root retains a name identifier, cannot match, and takes the NULL
default path instead of reading its value.

The source-predicted failure covers a struct-only table/projection and a mixed
scalar/struct projection. It does not establish failure for every nested encoding
or id-less import, and was not live-reproduced against the release BE.

**Action:** emit a complete nested identity tree, not an empty container field, or
reject the unsupported shape. Add BE-level nested-only/mixed projections, root
rename, and an id-less control. Schema reconstruction tests alone are insufficient.

### F13: Mixed Hive Layout Guard Misses Valid Mixtures

**Where:** [DuckLakeScanPlanProvider.kt:822-846,887-903](../src/dev/brikk/ducklake/doris/plugin/DuckLakeScanPlanProvider.kt#L887-L903),
[DuckLakeScanRange.kt:201-204](../src/dev/brikk/ducklake/doris/plugin/DuckLakeScanRange.kt#L201-L204).

The guard rejects only native files with non-null `partitionId`. Hive-layout
imports can exist in an otherwise unpartitioned table; a subsequent native INSERT
has neither partition nor mapping ID and bypasses it. Scan-wide path keys then
apply to ranges without path values. The FE-generated key/value length mismatch
can reach a BE `DORIS_CHECK`, instead of the intended FE rejection.

**Action:** validate every scanned file's actual path-backed column set, including
ordinary imports and synthetic inline ranges. Test Hive-plus-unpartitioned-native,
Hive-plus-ordinary-import, and differing Hive key sets with engine-prepopulated thrift.

### F14: Hive NULL Spelling Bypasses The Guard

**Where:** [DuckLakeScanPlanProvider.kt:609-623](../src/dev/brikk/ducklake/doris/plugin/DuckLakeScanPlanProvider.kt#L609-L623),
[HivePartitionPath.kt:31-35](../src/dev/brikk/ducklake/doris/plugin/HivePartitionPath.kt#L31-L35).

DuckDB classifies raw Hive partition values `NULL` case-insensitively as SQL NULL.
The connector guards only the Hive default sentinel and missing keys, so a VARCHAR
partition `p=NULL` or `p=null` is returned as non-null text. Separately, the parser
drops `p=`, which is a valid empty VARCHAR value, causing an unsupported-value error.

**Action:** match the reference engine's raw-value classification and preserve
empty strings. Until the connector's NULL path fill is implemented and validated
for the supported BE versions, reject all genuine NULL spellings. The pinned V2
reader already consumes `columns_from_path_is_null`; the upstream wire flag is
not absent. Test escaped literal text separately from raw NULL markers.

### F15: Unknown Bounds Leave Unsafe Global Statistics

**Where:** [DuckLakeIcebergCommitMapper.kt:24-30,153-155,184-197](../src/dev/brikk/ducklake/doris/plugin/DuckLakeIcebergCommitMapper.kt#L184-L197).

Returning null timestamp bounds is safe for this file's range pruning, but not
for the selected catalog's global merger. In catalog `v0.7.1`, an aggregate with
both bounds absent contributes nothing to existing global bounds, even when its
non-null value count is positive. Append a Doris timestamp in 2030 to a DuckDB
table bounded in 2024: the old global maximum can survive. DuckDB consumes that
metadata directly and can optimize a matching 2030 predicate to an empty result.

**Action:** fix the catalog contract to distinguish all-null input from non-null
data with unknown bounds, and preserve uncertainty across later appends/rebuilds.
Test mixed-engine append orders and optimizer-enabled DuckDB reads. The `0.7.1`
NaN/swapped-bound read guards do not fix persisted global metadata or intercept
DuckDB's direct reads. The mapper's claim that omission merely reduces pruning
coverage should be corrected with the fix.

### F16: Missing NaN Statistics Become False Certainty

**Where:** [DuckLakeIcebergCommitMapper.kt:121-155](../src/dev/brikk/ducklake/doris/plugin/DuckLakeIcebergCommitMapper.kt#L121-L155).

The pinned BE statistics collector does not populate `nan_value_counts`, but the
mapper converts absence to `containsNan=false`. DuckLake's NaN equality pruning
can then discard an actual NaN-containing file. This failure does not require
finite min/max bounds: the false flag alone excludes it. Missing null counts also
become zero, rather than unknown.

**Action:** preserve absent statistics as unknown and distinguish them from
explicit zero values. Test absent/zero/positive NaN maps, finite-plus-NaN and
all-NaN files, and filtered DuckDB read-back. Catalog `0.7.1` supports uncertainty
but cannot reconstruct it after the mapper supplies an incorrect false.

### F17: Write Commit Does Not Fence Earlier DDL

**Where:** [DuckLakeConnectorTransaction.kt:73-85](../src/dev/brikk/ducklake/doris/plugin/DuckLakeConnectorTransaction.kt#L73-L85).

The transaction decodes using its planning snapshot but calls `commitInsert`
without that snapshot. Catalog conflict tracking starts when commit is entered,
not when the BE began writing. A completed same-ID type change during the BE
write interval can therefore admit old-schema files/statistics after ALTER has
invalidated only the previously existing statistics.

For example, numeric extrema `2..10` from a planned INT write can be installed
after conversion to VARCHAR, where those bounds have different ordering semantics.
Doris has pre-execution schema checks and the catalog checks dropped references;
neither closes this later interval. This is not a claim that all concurrent DDL
escapes conflict detection.

**Action:** add an atomic commit precondition/conflict check spanning the planning
snapshot through commit. Test ALTER after target binding and before commit, with
a concurrent append as an allowed control. A standalone pre-commit check still races.

### F18: Read Widening Admits Invalid Unsigned Writes

**Where:** [DuckLakeIcebergSchema.kt:49-52](../src/dev/brikk/ducklake/doris/plugin/DuckLakeIcebergSchema.kt#L49-L52),
[DuckLakeTypeMapping.kt:81-86](../src/dev/brikk/ducklake/doris/plugin/DuckLakeTypeMapping.kt#L81-L86).

Widening unsigned types for reads does not enforce their write domain. An external
`uint16` column appears as Doris INT and is written as signed INT32. Values `-1`
and `65536` are accepted by those types but invalid for the catalog column. The
resulting committed file violates DuckLake's declared type; `uint32` has the same
problem through BIGINT.

**Action:** reject these writes until target-domain bounds are enforced before
file production, or add checked conversion. Test minimum, maximum, and both
out-of-range sides with DuckDB read-back. A CREATE-only guard is not enough.

### F19: An Iceberg Reserved Name Destroys User Values

**Where:** [DuckLakeIcebergSchema.kt:33-40](../src/dev/brikk/ducklake/doris/plugin/DuckLakeIcebergSchema.kt#L33-L40),
[DuckLakeWritePlanProvider.kt:85-90](../src/dev/brikk/ducklake/doris/plugin/DuckLakeWritePlanProvider.kt#L85-L90).

The pinned Iceberg writer recognizes `_last_updated_sequence_number` by name and
replaces its supplied values with NULL on INSERT. The connector passes ordinary
DuckLake names unchanged, without a lineage opt-in or reserved-ID distinction.
A nullable user column with this name reaches the mutation path.

**Action:** reject affected external-table writes until the BE gates lineage
handling on explicit metadata/IDs. Test a non-null supplied value in a nullable
column. This is source-traced, not a live INSERT result at the current pin.

### F20: Stale DROP Handles Target A Replacement Table

**Where:** [DuckLakeConnectorMetadata.kt:527-529](../src/dev/brikk/ducklake/doris/plugin/DuckLakeConnectorMetadata.kt#L527-L529).

DROP discards the handle's stable table ID and mutates by current database/name.
If another engine drops A and creates B under the same name after A's handle is
resolved, the stale operation drops B. Rename followed by name reuse is similar.

**Action:** enforce an expected table ID inside the catalog mutation transaction,
or provide a suitable drop-by-ID operation. Test stale handles after replacement
and rename/reuse; an ID check outside the transaction is not sufficient.

### F21: Smoke Maintenance Mutates The Shared Lake

**Where:** [compose/smoke.sh:197-209,867-940](../compose/smoke.sh#L867-L940),
[compose/step7-delete.py:60-66](../compose/step7-delete.py#L60-L66).

Smoke uses the shared Trino substrate's `ducklake` database and warehouse, lowers
retention to one second, and runs catalog-wide expiry/cleanup/orphan removal. It
also overwrites warehouse-root `_SUCCESS` and `data.parquet` and later deletes
them without checking previous ownership. Inlining configuration is changed
catalog-wide. This can destroy shared development history or foreign fixtures.

**Action:** allocate a smoke-specific database and run-unique warehouse prefix.
Never perform destructive maintenance or seed foreign-object names outside it.
This review deliberately did not execute that script.

### F22: Corpus Startup Can Kill Another Run

**Where:** [DorisCorpusReplayTest.kt:159-175](../test/src/dev/brikk/ducklake/doris/corpus/DorisCorpusReplayTest.kt#L159-L175).

Startup force-drops every PostgreSQL database matching `LIKE 'corpus_doris_%'`,
without checking owner, age, or active runs. SQL underscores are wildcards, making
the match broader than the intended literal prefix. Run-unique names do not
protect a concurrent run from this sweep.

**Action:** clean only current-run resources automatically. Make stale collection
an explicit operation with ownership/age/active-run checks, literal-prefix
matching, and quoted identifiers. Add a concurrent-run preservation test.

### F23: Development FE Is Public And Passwordless

**Where:** [compose/docker-compose.yml:20-24](../compose/docker-compose.yml#L20-L24),
[compose/smoke.sh:178-182](../compose/smoke.sh#L178-L182).

Host ports bind all interfaces while the advertised SQL account is root without
a password. On a reachable development server, this exposes administrative SQL,
not just a health endpoint.

**Action:** bind development HTTP/MySQL to loopback, avoid publishing internal
RPC/edit-log ports, and make authenticated remote access an explicit opt-in.
The exposure depends on host/network reachability, not merely container startup.

### F24: Repeat Smoke Can Exercise An Old Plugin

**Where:** [compose/smoke.sh:95-116](../compose/smoke.sh#L95-L116).

The script replaces plugin JARs in a mounted volume, then uses plain Compose
`up -d`. An existing unchanged FE service is not restarted, although plugins load
at startup. Tests can report success against old loaded code, and replacing JARs
beneath a live classloader risks mixing old and newly loaded classes.

**Action:** stop the FE before replacing the plugin, explicitly restart/recreate
it, and assert the running plugin's build identity before correctness checks.

### F25: Smoke Success Is Not A Correctness Gate

**Where:** [compose/smoke.sh:618,827-831,874-897,924-942](../compose/smoke.sh#L924-L942),
[compose/w2-insert.py:63-67](../compose/w2-insert.py#L63-L67).

Several wrong results only print `CHECK`; W1's `LIVE-GREEN` summary is unconditional.
GC's final condition does not assert the referenced table's read-back count.
The Python write helper prints DuckDB rows without comparing expected tuples, so
the cross-engine label can accompany swapped/corrupted values with a correct count.

**Action:** accumulate assertion outcomes, fail unexpected mismatches, and derive
summaries from those outcomes. Known gaps should be explicit, version-scoped
expected failures. Compare exact typed rows in both engines, not just counts.

### F26: Upstream Cast Erasure Makes Pushdown Unsafe

**Where:** [DuckLakePredicateConverter.kt:72-78](../src/dev/brikk/ducklake/doris/plugin/DuckLakePredicateConverter.kt#L72-L78),
pinned Doris `ExprToConnectorExpressionConverter.java:108-109`.

The FE converter discards casts. For an INT file containing `10`,
`CAST(id AS STRING) LIKE '1%'` can arrive as a bare-column LIKE. This connector
turns it into bounds `1..2`, and the catalog interprets those as integer bounds,
discarding the matching file.

**Action:** preserve casts or mark unproven conversions unpushable in Doris.
Connector type checks can mitigate some shapes but cannot recover erased semantics
in general. Add an FE-to-result cast-plus-filter regression. Ownership is primarily
upstream; keeping the full residual expression does not make unsafe file pruning safe.

## Strengths

- **S01: The execution boundary is well chosen.** The connector owns catalog semantics
  and planning, while the BE owns Parquet execution. Avoiding a second query engine
  or a redundant JVM data path is a substantial simplification.
- **S02: Responsibilities are mostly recognizable.** Provider/lifecycle, metadata,
  ranges, type/partition translation, commit mapping, and blob-store operations
  have clear homes. Small pure helpers are generally easy to inspect and test.
- **S03: Many safety instincts are right.** Unsupported inline deletes and partial
  data-file history fail loudly. COUNT/LIMIT eligibility is deliberately narrow.
  Residual predicates remain enforced by the BE. Those choices should be retained.
- **S04: Interop testing is better than mock-only testing.** Real DuckDB/PostgreSQL
  fixtures, actual Parquet round trips, upstream Iceberg parser oracles, and thrift
  goldens test meaningful contracts. The corpus has already found real bugs.
- **S05: Recent maintenance changes address real ownership hazards.** Catalog-wide
  known references include dropped-but-unexpired tables and scheduled files, and
  schema/table/root path resolution is explicit. That is progress even though
  F01 shows identity normalization still needs work.
- **S06: Commit assembly has a sound core.** All fragments are mapped before one
  catalog commit; an empty insert creates no snapshot. Catalog atomicity and
  active-reference checks provide real protection, though not the entire write interval.
- **S07: Dependency isolation is intentional.** Doris artifacts are compile-only,
  local Maven resolution is scoped to Doris, and the plugin owns its Iceberg SDK.
  The classloader rationale is unusually well documented.
- **S08: Historical statistics use the actual SPI contract.** The three-argument
  snapshot-aware overload is a concrete correctness improvement for planner estimates.

## Weaknesses

### W01: Semantic Boundaries

The main weakness is not Kotlin syntax or formatting. It is treating a transport
similarity as a semantic guarantee: an Iceberg-shaped sink does not establish
DuckLake partition values, reserved-column behavior, column ordering, or imported
field identity. Likewise, a snapshot ID does not establish one physical metadata
view, and null statistics do not automatically stay unknown through aggregation.

Each bridge needs an explicit producer/consumer contract and a test that composes
both ends. More local abstraction layers would not repair these missing contracts.

### W02: Test Confidence

Coverage is strongest for individual features and weaker at intersections:
partition evolution plus pruning, type degradation plus filtering, schema changes
plus in-flight writes, mixed imported/native files, and temporal delete history.
Several tests assert that metadata was emitted rather than that the engine returns
the right values. Broad skips and nonfatal smoke mismatches inflate apparent coverage.

The normal suite being green is useful but cannot certify the advertised read/write
surface. Make accepted cases strict and known exclusions explicit before investing
in a larger raw test count.

### W03: Maintainability

Most small helpers are readable. `DuckLakeScanPlanProvider` is now over 1,000 lines
and combines metadata collection, eligibility decisions, inline materialization,
partition interpretation, credentials, and wire construction. The first useful
refactoring is a coherent per-plan metadata view, because it fixes F07 and reduces
repeated lookups. Avoid splitting every few lines into a new class merely to pass lint.

Comments often explain valuable historical discoveries, but some now assert false
invariants. The project needs less duplicated chronology and more short, current
contracts linked to regression tests. Detekt success is code hygiene, not proof
that those contracts hold.

### W04: Operations

This remains a developer-oriented integration: shared substrate, mutable local
engine builds, permissive default network exposure, limited lifecycle/progress
reporting, and no checked-in packaged-plugin compatibility gate. FE-side inline
materialization and eager GC listing also need explicit resource budgets before
being considered production mechanisms.

## Recommended Sequence

### Top Five Priorities

This is the initial risk/reward ranking, not a renumbering of findings. Complexity
includes regression coverage: **Low** is a localized change using an existing
contract; **Medium** spans related components or an integration fixture matrix;
**High** needs a cross-project contract/authorization change. These are estimates,
not elapsed-time promises; unavailable engine builds can block live verification.

| Rank | ID | Deliverable | Complexity | Why This Priority / Completion Evidence |
|---|---|---|---|---|
| 1 | F01 | Prevent orphan cleanup from deleting referenced objects through URI alias mismatches. | **Medium** | Direct live-data loss. The code change should be small, but must preserve exact object keys and protect mixed absolute/relative, scheduled, and dropped-table references. Regressions must reproduce the real S3 lister's canonicalization. |
| 2 | F02 | Enforce authorization matching maintenance's actual scope. | **High** | Table-scoped authority currently reaches other tables' history. Full closure may require an upstream authorization/SPI seam and role-based FE tests. A fail-closed restriction is a smaller interim mitigation, not proof that full authorization is implemented. |
| 3 | F03 | Require full-schema write order for the positional Iceberg sink. **Implemented locally; live verification pending.** | **Low** | Silent corruption on an ordinary INSERT, with an existing SPI flag as the remedy. The declaration regression and schema-contract tests pass; exact reversed/partial-column and partitioned INSERT results through FE/BE and DuckDB remain to be verified. |
| 4 | F21 | Isolate smoke databases, warehouse prefixes, and all destructive fixture cleanup. | **Medium** | Protects shared development data and enables safe live verification of other fixes. Thread run-specific ownership through shell/Python fixtures and prove pre-existing unrelated objects/history survive. |
| 5 | F04 | Make bucket pruning retain unpartitioned and retired-spec files safely. | **Medium** | Silent row loss after valid partition evolution. Establish the complete file universe, apply only proven compatible specs, and test exact retained files across unpartitioned-to-bucket, bucket-count, and key-order changes. Conservative retention is acceptable; speculative pruning is not. |

**Operational prerequisites:** fix F21 before using smoke to validate another
item, and F22 before concurrent corpus runs. F24/F25 must also be addressed before
treating smoke's own green summary as completion evidence; until then use explicit
isolated assertions and verify the loaded artifact. If the FE is reachable by
untrusted hosts, promote **F23** to immediate containment ahead of this ranking.
F20 and F07 are the next high-risk correctness candidates after these five.

### Broader Sequence

The stages below group the already identified items, rather than creating new
claim IDs. Use the specific finding/nit IDs when assigning work.

1. **Protect data and the development host.** Fix F01/F02/F20, isolate smoke/corpus
   cleanup, and bind ports safely. Restrict affected maintenance until then.
2. **Make validation trustworthy.** Restart and identify the actual plugin, make
   smoke assertions fatal, assert cross-engine tuples, and constrain corpus skips.
3. **Close silent read/write errors.** Start with the small full-schema-order fix,
   then bucket/type-domain pruning, Unicode, snapshot consistency, and historical
   deletes. Use explicit unsupported guards where a correct bridge is unavailable.
4. **Repair shared contracts.** Coordinate unknown global stats, NaN flags,
   write-snapshot conflict checks, cast preservation, field mappings, and temporal
   partition semantics with their catalog/FE/BE owners. Add two-ended regressions.
5. **Establish a supported matrix.** Record exact FE/BE/catalog/DuckDB versions,
   separate Java-17 plugin checks from newer test tooling, and rerun isolated live
   value-level coverage before expanding support claims.
6. **Then reduce debt and add features.** Reconcile current documentation, trim
   stale comments/binaries/suppressions, improve planning/GC resource bounds, and
   resume row DML, ALTER, compaction, or production inline transport as priorities allow.

The project does not need a wholesale rewrite. It needs stricter semantic contracts,
less permissive validation, and a smaller set of genuinely proven support claims.
